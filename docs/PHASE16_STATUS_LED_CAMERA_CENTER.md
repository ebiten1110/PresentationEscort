# Phase 16: RGB状態LED、首優先・本体旋回、中心合わせ可視化

## 何を変更したか

**ESP32ファーム更新が必要**: `esp32/src/light_control.cpp` の状態LEDを安全制御と連動。
現在のハードウェア設定は共通カソードRGB LED 3個（各色ごとに抵抗）、GPIO 25=R、26=G、27=B。実機の接続方式がこれと異なる場合は必ず先に配線を検証する。現在の `esp32/include/config.h` は `SWITCH_PIN=26` も定義しているため、別途物理スイッチをGPIO26へつなぐ設計はピン競合に注意。

| 色 | 実際の判定 |
|---|---|
| 赤 | 停止・SAFE（待機解除済み）・ESTOP、ファームウォッチドッグ異常 |
| 黄色 | 操作者が認証済みGUIでジェスチャー待機をON、ESP32 DISARMED、Piが有効期限1.2秒の黄色更新を継続 |
| 白 | ESP32の安全ウォッチドッグがARMED。Pi側のAUTO表示を無条件には信用しない |

ファームウェアがARMEDから抜けたら黄色リースを即座に破棄して赤へ戻す。Piとの通信が途絶えた場合は黄色の更新がなくなるので自動的に赤へ戻る。物理的なサーボの外部電源切断はこのLEDでは行わない。

**追従:** 顔の水平ずれが小さいときは首Yaw。ずれが大きくなり、首が±3°校正済み限界へ近づいて、ESP32の首/本体状態が新鮮なときだけ、短い左右旋回を追加する。旋回終了のIDLE確認と待機時間が必要。首・旋回動作回数の累積制限は設けていない。完全に人物を見失ったらソフトウェア安全ゲートがSTOPを発行するので、無検出のまま見失った方向へ走行・旋回し続けることはしない。最後に見えた方向はGUIで表示する。前後の歩行は未校正・無効。

**カメラGUI:** 実際に狙う顔/肩/上半身の座標（オレンジの輪）、光学画面中央の座標（白い十字/円）、中心へ向かう矢印、中心からの水平/垂直誤差px、首/本体旋回候補の境界線、および最後に見えた方向を表示。背景の赤黄白ステータスランプは「期待・報告ステータス」で、LEDや電源を物理的にセンシングしていない。

## 実機の手順

最初にロボットを支持台に固定し、サーボの可動域・外部電源と物理遮断を再確認する。

1. WindowsとPiの起動中プロセスをCtrl+Cで停止し、双方ともブランチ `feature/pc-gpu-follow-2026-10-28` で `git pull --ff-only`。
2. RGBの共通極・抵抗・ピン配線を確認してから、サーボ外部電源をOFFにしてESP32をWindows USBへ接続。PC側 PlatformIO で新しいファームウェアをアップロード。
   ```powershell
   cd "$HOME\PresentationEscort-demo"
   & ".\.venv\Scripts\python.exe" -m platformio run -d esp32 -e esp32dev -t upload --upload-port COM3
   ```
   COM3は例。実際のESP32ポートへ変更し、書き込みエラー時はシリアルモニター等の排他利用を解除。アップロード速度が原因で接続失敗する際は `esp32/platformio.ini` の `upload_speed=115200` への切替を検討。
3. ESP32をPiにUSB接続して、既存のGPUサーバー・SSHトンネル・Pi実機プログラムを起動。起動フラグは実機の校正・固定・遮断が確認できたものに限る（前回と同じ）。
4. 操作コンソールを強制再読込、新しいトークンで認証。**赤**が出るか確認。手動で「ジェスチャー追従を待機」をON → **黄色**。両手挙げで追従開始しARMEDになったら **白**。
5. 対象の左右移動を少しずつ試し、顔から中心への矢印とdx/dy表示、首Yaw指令が一致するか確認。画面端へ近づいた場合だけ本体が旋回するかを確認。
6. ロストまたはSTOPで動作が中断し、LEDが赤またはジェスチャー再待機の黄色になることを確認。通信断・ESTOP・緊急異常では必ず物理遮断を使用すること。

**注意:** ESP32のPWM/LEDはシミュレーションで実配線や光量を検証できない。RGBが単色/共通アノードならソフト設定と配線を合わせる必要がある。Pi側のUIだけ更新しても古いESP32ファームウェアではLEDがこの仕様どおりには動かない。
